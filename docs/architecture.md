# Architecture

How `envik generate` turns files and values into a `.env`, and where each
step lives. The rules for changing the code are in
[AGENTS.md](../AGENTS.md); the reasons behind the shape are in
[decisions.md](decisions.md).

## The flow

```
command line ──► cli/generate.rs ──────────────────────────────► stdout / -o
                   │ reads -i/-I files (in order), -e KEY,           ▲
                   │ --env-override-prefix variables, the seed       │
                   ▼                                                 │
            Generator::new(sources) ── parse.rs ──► EnvFile per input │
                   │  env_flag / env_override / seed                 │
                   ▼                                                 │
            Generator::generate()                                    │
                   ├─ values: files, later winning, then env flags   │
                   ├─ env overrides applied (existing keys only)     │
                   ├─ resolve: ${NAME}, ${NAME:-default}, $(rand n)   │
                   └─ render.rs: template layout + final values ─────┘
```

1. **`cli/generate.rs`** does all the I/O. It puts `-i` and `-I` back in
   command-line order using clap's argument positions, reads the files
   (a missing `-I` is skipped), looks up `-e KEY` and the prefixed
   variables, and reads or makes the seed. Every failure is collected into
   one list before anything else runs.
2. **`Generator::new`** parses every input with `parse.rs`. It cannot exist
   with an invalid file: all parse errors come back together. The first file
   becomes the template; every file's active entries go into `values`, later
   files winning.
3. **`env_flag`** sets a value at once. **`env_override`** is stored and
   applied in `generate`, so it wins over env flags whatever order the calls
   came in, and only for keys that exist.
4. **`generate`** applies the overrides to a copy of `values`, resolves every
   key against the final values (a depth-first walk that reports each missing
   reference and each cycle once), and hands the result to `render`.
5. **`render.rs`** walks the template's lines: unchanged literal lines are
   copied byte for byte, changed ones get only their value span replaced,
   commented `# KEY=` lines are turned on or dropped, and keys the template
   lacks are appended after a `# ----` line.
6. **`cli/generate.rs`** creates the seed file if one was made up (only now,
   after success), then writes the output.

## The model (`env.rs`)

- `EnvKey`: a valid variable name; only `EnvKey::new` builds one.
- `EnvValue`: a value as parts, `Literal`, `Ref { name, default }` or
  `Call`, kept normalized (no empty or adjacent literals) so equal values
  compare equal. Quotes and escapes are already resolved.
- `EnvFile`: every line of a file, kept with its original text so the
  template can be written back. `EnvEntry` holds the key, the value, the raw
  line, the value's byte span in it, and whether it is active or commented.
- `EnvMap<V>`: a value per key in first-appearance order; `EnvValue` before
  resolution, `String` after.

## The parser (`parse.rs`)

One `Cursor` per line over a `Peekable<CharIndices>`, one method per grammar
rule, and the grammar itself in the module doc. Rules that end the line take
the cursor by value. A commented entry that does not parse is text, not an
error. Values are read unquoted, in `'...'` (literal) or in `"..."`
(escapes `\n \" \\ \$`); after `$`, `{` starts a reference and `(` a call.

## Secrets (`rand.rs`)

`Seed::new` turns the seed text into a BLAKE3 key with `derive_key` and a
fixed context. `$(rand n)` is a keyed BLAKE3 hash of the variable's name, the
call's position in its value, `"rand"` and `n`, each length-prefixed, read as
`n` bytes from the XOF output and mapped onto a 64-character base64url
alphabet (no bias). The value depends on nothing else, so other lines never
change it. The seed is the only secret: anyone with it can recompute every
value, and a guessable seed can be brute-forced from one generated value.

## Release pipeline

- `ci.yml`: fmt, clippy `-D warnings`, tests, on pull requests and `main`.
- `prepare-release.yml` ("Prepare release", manual): `cargo release` with
  `release.toml`, git-cliff writing `CHANGELOG.md`, pushed with a deploy key
  so the tag triggers the next workflow.
- `release.yml` ("Release", generated by cargo-dist from
  `dist-workspace.toml`): builds every target, creates the GitHub Release with
  the shell and PowerShell installers, and publishes `@envik/cli` to npm. The
  npm package downloads the binary from that GitHub Release when installed.
